## سياسة أسماء المقاسات

`SizeNamePolicy` عقد الإصدار 1؛ لا ينبغي تغيير قوائمها أو دلالة SQL بصمت، لأن migration والقيد يعتمدان عليها. أي تغيير لاحق يحتاج migration وفحصاً للبيانات.

- إزالة المسافات الطرفية، وتوحيد قائمة محددة من مسافات Unicode إلى مسافة عادية، ودمج المسافات المتتالية داخل الاسم.
- إزالة قائمة محددة من المحارف غير المرئية/اتجاه النص، وتوحيد الحروف الإنجليزية ASCII a–z إلى A–Z فقط. لا تحويل أرقام أو شرطات أو كلمات عربية، ولا توحيد حالة الحروف غير الإنجليزية.
- رفض الاسم الفارغ بعد التطبيع، أو الأطول من 128 محرفاً، أو المحارف التحكمية غير المسموحة. نطاق أسماء المقاسات لا يقبل محارف surrogate/رموز خارج BMP؛ لم يكن هناك سبب تجاري لاستخدامها في المقاسات.
- `3 سنه` و`3 سنوات` مختلفان؛ `3-4` و`34` مختلفان؛ `é` و`É` مختلفان. مسافة NBSP ومحرف U+200B لا يجعلان اسماً جديداً.
- إبقاء النص الخام للعرض؛ المفتاح المنفصل للمقارنة والحماية. كمية صفر صحيحة؛ السالب أو القيمة التي لا تمثل integer صالحاً مرفوضة.

اختبار SQLite يقارن `SqlKey` و`SqlValid` مع التطبيق لكل محرف في القائمتين وحالات المسافات والحروف والأسماء المتميزة والتحكم والطول والرموز خارج المجال. استُخدم `BINARY` للفهرس، ولم يُعتمد على `NOCASE` أو دلالة Unicode مختلفة بين C# وSQLite.

## التوافق مع السلال والمحاولات والطلبات القديمة

السلال القديمة بلا `ProductSizeId` تبقى قابلة للقراءة؛ مطابقة الاسم الفريدة ترقيها إلى الهوية. الغموض، بما فيه صف صفري وآخر موجب، لا يُحل باختيار صف. حذف/إعادة إنشاء صف أو منتج لا ينقل السلة الجديدة ذات الهوية إلى بديل بالاسم نفسه. تغيير 3 سنه إلى 4 سنه مع إبقاء ID يرفض عند اختلاف مفتاح لقطة الاختيار.

hash طلب Checkout الجديد يحمل بادئة `V2:` ويضم الهوية، مع الاحتفاظ بحساب hash الإصدار القديم للتحقق من محاولات مكتملة قبل الترقية. عند وجود Attempt ID مكتمل، يُسترجع الطلب نفسه أو يُرفض تغير محتواه؛ لا تُنشأ محاولة جديدة بسبب تغير عقد السلة. `GetCheckoutReceiptAsync` بقي يعيد الهوية والرقم فقط. pending session record يحمل Version=2 وhash يتضمن هوية المقاس، مع قراءة سجل Version المفقود بصيغته القديمة. الاختبار أثبت قبول محاولة قديمة مكتملة بعد إضافة الهوية، مع بقاء طلب واحد وخصم واحد.

`OrderItems.ProductSizeId` nullable للصفوف التاريخية. **لا backfill بالاسم الحالي**: حتى مطابقة اسم واحد لا تثبت أنه الصف الذي خصم منه الطلب القديم. انتقالات الحالات العادية التي لا تعدل المخزون تستمر، وإعادة نفس الحالة no-op. الإلغاء/إعادة التفعيل الذي يحتاج خصماً أو استعادةً بلا هوية موثوقة يتوقف برسالة مراجعة إدارية. يلزم دليل مستقل من بيانات/نسخة تاريخية قبل أي تسوية لهذه الطلبات؛ لم يُنفّذ إصلاح بيانات إنتاج.

لم يتغير تصنيف Sandbox أو توليد أرقام الطلبات أو حجوزاتها الدائمة أو تدقيق تعديل الرقم أو ربط SalesHistory بهوية الطلب. لم تُعدل snapshots المالية بسبب تغيير رقم أو مقاس لاحق. لم تُضف FK من OrderItem إلى ProductSize تمسح اللقطة عند حذف المقاس.

1. preflight داخل معاملة الترقية وقبل تغير المخطط: يرفض أسماء/كميات غير صالحة، وتصادمات المفتاح لكل منتج، وهويات غير مطابقة لتمثيل GUID الذي تستعمله EF/SQLite، وروابط منتج مفقودة. يظهر قيد `InvalidOrAmbiguousProductSizes` عند التوقف. لا دمج أو حذف أو تصحيح كميات أو تغيير IDs.
2. إضافة `ProductSizes.NormalizedName`، وحساب المفاتيح من الأسماء الخام دون تعديل الاسم أو الكمية، ثم فهرس فريد `(ProductId, NormalizedName)` بــBINARY.
3. إضافة `OrderItems.ProductSizeId` nullable، وترك التاريخي NULL.
4. إنشاء ledger دائم `ProductSizeIdentities` من الصفوف الحالية، ومنع إعادة إدخال ID حُذف أو تغيير هوية/مالك صف قائم. لا يحاول استنتاج IDs لصفوف حُذفت قبل الترقية.
5. triggers تتحقق من المفتاح المحسوب ومن الاسم والهوية وكون الكمية integer ضمن 0..Int32.MaxValue، بما فيه الكتابة التي تتجاوز الخدمة.

اختبارات الترقية تبدأ من المخطط السابق وتفحص الصور والمقاسات والكميات والسجل وحجوزات الأرقام والتدقيق وtriggers الأرقام السابقة. تتوقف atomically عند التكرار الخام أو بعد التطبيع، أو اسم غير مرئي فقط، أو كمية سالبة، أو هوية غير قابلة للربط. اختُبر Down/Up على fixture معزولة؛ `has-pending-model-changes` لا يجد اختلافاً بين النموذج والـmigration.

### قبل النشر والتراجع

- الحصول على snapshot صحيحة ومتسقة من قاعدة الإنتاج أثناء توقف الكتابات، والاحتفاظ بنسخة احتياطية قابلة للاسترجاع مع التطبيق المطابق لها. تشغيل التشخيص على النسخة، وحفظ نتائجه، وتجربة migration عليها أولاً.
- مراجعة كل تعارض مقاسات ودليله وتحديد stock الصحيح يدوياً من مصدر موثوق. لا حذف/إعادة إنشاء المنتج أو جمع الكميات كحل آلي. مراجعة أثر NULL التاريخية على الطلبيات التي قد تحتاج إلغاءً أو إعادة تفعيل.
- إيقاف النسخ القديمة/الـcircuits القديمة والكتابات، ثم ترقية schema والتطبيق معاً بعد اجتياز نسخة الاختبار. الكود الجديد يحتاج العمودين والقيد والledger؛ الكتابات القديمة التي تغير الأسماء أو تنشئ صفوفاً بلا المفتاح ستفشل على المخطط الجديد. تشغيل نسخ قديمة وجديدة معاً ليس خطة نشر متوافقة.
- التراجع المفضل إصلاح لاحق أو استعادة **قاعدة وتطبيق متطابقين** من snapshot بعد إيقاف الكتابات ومعالجة العمليات التي حصلت بعدها. لا تشغيل الإصدار القديم على schema الجديدة.
- Down يحذف معلومات هوية المقاس الجديدة والledger وقيد التفرد. استخدامه بعد إنشاء طلبيات جديدة يفقد هذه المعلومات، فلا يصلح كتراجع روتيني مع استمرار العمليات؛ تجربة Down هنا تثبت سلوك fixture فقط وليست إذناً بتنفيذه على الإنتاج.

لم تُطبق الترقية على قاعدة المشروع أو الإنتاج، ولم تُنفذ هذه الخطوات خارج fixtures.

## فحص الواجهة الفعلي

أُجري عبر Chrome باستخدام مهارة computer-use وأداة browser، على خادم fixture فقط، بحساب وبيانات اصطناعية.

- سطح المكتب: اختيار 3 سنه بكمية متاحة 3؛ إضافة قطعة؛ تنقل/استعادة السلة؛ تأكيد الطلب وظهور النجاح والرقم؛ جلسة Blazor ثانية تعرض الكمية 2. هذه جلسة/circuit جديدة في تبويب آخر، وليست ملف متصفح منفصلاً.
- الهاتف: viewport CSS فعلية 390×844، و`documentElement.scrollWidth=390`؛ اختيار المقاس والسلة وCheckout وRTL؛ إرسال بالضغط المزدوج. تدقيق DB للقراءة فقط وجد Orders=1، Attempts=1، وItemsWithSizeIdentity=1، والكميات 2/4/2/4. عُرضت لقطات الفحص أثناء العمل، وأعيدت أبعاد المتصفح الافتراضية عند الانتهاء.
- الإدارة: التعديل عرض المقاسات مع كمياتها الصحيحة؛ تكرار 2 سنه بمسافة NBSP رُفض مع الصفوف والمدخلات؛ تصحيحه وحفظه لم ينشئ منتجاً آخر. الإضافة بصفين S و`s` رُفضت، والكمية الفارغة رُفضت، وM=0 قُبلت؛ نُشر المنتج من زر النشر وتأكيده الحقيقيين.
- الإلغاء: اختيار «ملغاة» في القائمة ترك DB بحالة New ومخزون 2 قبل الضغط على حفظ الحالة. بعد الحفظ عاد 3 سنه إلى 3 فقط؛ إعادة التفعيل أعادته إلى 2، مع بقاء طلب واحد. المقاسات الأخرى بقيت 2/4/4.
- سلة تشير إلى fixture أوقفت ثم أُعيد إنشاء خادم بمنتج آخر بالاسم نفسه: العنصر القديم ظهر برسالة مراجعة، ولم ينتقل إلى المنتج الجديد أو تُمسح السلة خفية.

نموذج الإدارة الحالي لا يملك أزرار حذف/تحريك صفوف المقاسات؛ لم تُضف أزرار أو تصميم جديد. سيناريو حذف الصف الأوسط وقلب ترتيب الصفوف فُحص عبر مدخلات خدمة التعديل، وليس كتفاعل UI غير موجود. لم تُجرّب أجهزة هاتف فعلية أو متصفحات أخرى أو المتجر الحي، ولم يُفتعل انقطاع شبكة في المتصفح؛ retry/محاولات متزامنة/مكتملة فُحصت في runner على SQLite، واستعادة الصفحة فُحصت تفاعلياً.
