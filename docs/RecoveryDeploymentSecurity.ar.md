## D. Deployment Safety — حماية البيانات والتعافي

المسارات المعتمدة بقيت: المستودع `/var/www/larafashion/LaraFashion`، التطبيق `/var/www/larafashion/publish`، القاعدة `/var/www/larafashion/data/larafashion.db`، الصور `/var/www/larafashion/uploads`، النسخ `/var/www/larafashion/backups`، الإصدارات `/var/www/larafashion/releases`، الخدمة `larafashion.service`، الصحة loopback على `http://127.0.0.1:5000/health`. القفل المشترك ثابت، ولا يُحذف عند نهاية العملية. التزامن في Actions وflock يخدمان مستويين مختلفين؛ إثبات flock الفعلي ما زال PENDING.

على Linux يتطلب القفل ملفًا عاديًا برابط واحد، يملكه root أو مستخدم النشر ولا تقبل فيه كتابة group/others؛ الأب يملكه root أو مستخدم النشر، والأب المشترك القابل للكتابة يحتاج root وsticky bit كما في `/tmp`. الإنشاء يستخدم noclobber وumask 077؛ بعد الفتح تُقارن dev/inode لـFD9 مع الاسم. لا chmod/chown أو حذف تلقائي لمعالجة قفل غير موثوق: يتوقف المسار قبل Git/stop. اختبارات MSYS تتجاوز **فحوص POSIX/FD هذه فقط** داخل harness المعزول الموسوم، ولا تعدها PASS؛ الإنتاج يتطلب Linux. قبول الملكية والـhard links والـFIFO/الـsymlink واستبدال الملف الفعلي ما زال PENDING على Linux.

1. قبل إيقاف الكتّاب: مسارات دائمة منفصلة وصلاحيات ومستخدم الخدمة وEnvironmentFile وDP keys خارج الإصدار والويب، مساحة كافية، SHA نظيف، Build/Publish Release خاصان، عقد الأداة والحزمة والـmanifest. غياب إعداد أو توافق يمنع التقدم.
2. نية stop محفوظة؛ التحقق من systemd/MainPID وfuser للقاعدة وWAL وSHM. لا قتل لعملية مجهولة، ولا افتراض أن فشل start يعني عدم استقبال معاملات.
3. SQLite Online Backup API يولد `before.db` خاصًا بالمحاولة؛ يثبت سلامته وforeign keys والبصمة وثبات المصدر ومقارنة بيانات الأعمال. لا cp لملف db نشط، ولا حذف WAL/SHM، ولا قاعدة بديلة فارغة. اختبار WAL شمل سجلاً ملتزمًا في WAL فعليًا وحافظ على journal المصدر.
4. خطة حديثة من هذه النسخة، تثبيت هوية ملف الهدف، rehearsal مستقل، إثبات أهلية قبل الترحيلات، ثم مقارنة جميع بيانات الأعمال السابقة والحراس والأدلة قبل تشغيل التطبيق. مصدر الإثبات السابق للهوية، إن لزم، يبقى منفصلًا ومحميًا ولا يُستبدل بنسخة أحدث.
5. تبديل الملفات يتطلب نفس جهاز التخزين وهوية المجلدين ووجهة خالية. كل rename يُفحص؛ لا استبدال للصور أو DB أو DP keys أو إعدادات الخدمة. التبديل مكوّن من عمليتي rename أثناء توقف الكتّاب؛ توجد فجوة بينهما وليست معاملة ذرية واحدة. SIGKILL/إعادة التشغيل في هذه الفجوة يحتاجان فحصًا يدويًا للحالة والمجلدات، ولا يوجد ادعاء تعافٍ تلقائي من فقد الطاقة.
6. إن لم تُحاول الخدمة التشغيل: التعافي يحتاج نسخة **هذه المحاولة** وإصدارًا سابقًا ذا manifest وبصمة DLL ومخطط متوافق، وهوية مجلد صحيحة وإثبات عدم تغير الأعمال. يسجل restore intent ويحفظ `before-restore.db` الحالية قبل restore عبر API إلى الملف الموجود نفسه. بعد تثبيت نية تشغيل الإصدار السابق لا يسجل Recovered إلا بعد GET يطابق SHA/مخطط الإصدار السابق وهوية DB وMainPID، مع إعادة التحقق من DLL والمخطط الفعلي. غياب عقد الصحة في إصدار قديم أو فشله يؤدي إلى stop وManualRecoveryRequired دون restore ثانية. نجاح التعافي يبقي exit فاشلاً؛ ليس نشرًا ناجحًا.
7. إن كانت هناك محاولة start أو كتابة أعمال لاحقة أو فشل restore/rename أو حالة غير محسومة: توقف آمن و`ManualRecoveryRequired`، دون replay تلقائي. القاعدة الحالية والنسخ والمرشح والإصدار السابق وسجل المحاولة محفوظة. لا نقل نسخة تاريخية فوق أعمال أحدث.
8. Completed يتطلب GET بعقد JSON يطابق SHA والمخطط وهوية DB وMainPID. لا `--insecure` أو اتباع redirects. اختبار Nginx/TLS والدومين وSSH على الخادم الحقيقي منفصل وPENDING.

لا حذف لأي backup أو زوج تعافٍ أو إثبات أو key ring. النتائج العامة ملخصات فقط؛ قواعد fixtures وخطط الأدلة التفصيلية وسجلات الصيانة داخل TEMP/المحاولة الخاصة، خارج Git وArtifacts العامة. لا قيم مفاتيح أو إعدادات إنتاج سرية في التقرير. وجود sysadmins موثوقين وملكية المجلدات والصلاحيات الفعلية وغياب كتّاب غير مسجلين شروط تشغيل يجب قبولها على الخادم.

### Off-site Backup — تصميم مقترح غير مفعل

اقتراح قابل للتنفيذ بعد موافقة منفصلة: نسخة يومية خاصة بهدف RPO متفق عليه، ونسخة قبل كل نشر، مع احتفاظ مبدئي 14 يومية و8 أسبوعية و12 شهرية قابل لتعديل المساحة والحاجة. هذه أرقام سياسة مقترحة وليست أوامر تنظيف؛ النسخ اللازمة للتعافي وآخر نسخة سليمة ومصادر الإثبات ذات الحفظ الطويل لا تدخل حذفًا تلقائيًا.

كل generation له معرف وتوقيت وSHA الإصدار وschema/manifest ونتائج integrity/FK، snapshot SQLite من Online Backup API، أرشيف جميع الصور مع قائمة SHA256 ومسارات نسبية، وبيان hash للملفات. لجعل DB والصور زوجًا متسقًا تؤخذ تحت نفس قفل الصيانة وبعد إيقاف كتّاب DB/الصور المعروفين في نافذة معتمدة؛ لا يكفي نسخ صور أثناء تغييرها. تُحفظ DP keys والإعدادات اللازمة للاستعادة داخل حزمة سرية مشفرة منفصلة عن البيانات العامة، ومفتاح فك التشفير خارج الخادم وبصلاحيات ضيقة.

ترسل الحزمة المشفرة لاحقًا إلى مخزن خاص خارج الخادم/Boot Volume وبحساب أو نطاق أعطال مستقل مع نسخة offline لدى المسؤول؛ لا GitHub Artifacts عامة ولا بيانات زبائن في Git. تعتبر النسخة مكتملة فقط بعد التحقق من SHA256 في الوجهة وقابلية فك التشفير وقراءة manifest. فشل النقل أو التحقق لا يحذف النسخ المحلية. لا اختيار خدمة مدفوعة أو ربط حساب أو جدولة ضمن هذه المهمة.

اختبار استعادة شهري معزول على Linux: تنزيل generation واحدة، تحقق hashes والتشفير، integrity/FK على DB مستقلة، مقارنة الأعمال بما كانت عليه **تلك النسخة**، تحقق الصور المشار إليها وسجل DP/schema/version، ثم تشغيل الإصدار المتوافق وGET واختبار جلسة اصطناعية. قياس RTO وتوثيق النتيجة وآخر نسخة نجحت. لا استعادة فوق المتجر الحي ولا فرض أعداد الاستعادة التاريخية.
