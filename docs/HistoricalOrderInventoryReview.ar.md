## C. التصميم والأهلية وفصل الهوية عن التسوية

تظل `OrderItems.ProductSizeId=NULL` للأسطر التاريخية. قرار المدير يُحفظ في جداول مستقلة باعتباره مقصد حركة إدارية لاحقة، ولا يُكتب كهوية شراء أصلية. أسطر الطلب الجديد تستمر في استعمال الهوية الثابتة المحفوظة أثناء Checkout.

`NULL` وحدها لا تفتح مسار التسوية. أضيف سجل `HistoricalOrderItemEvidence` لإثبات أن السطر نفسه كان موجوداً قبل ترقية هوية المقاسات، بمعرفاته ولقطة بياناته الأصلية المطابقة. البصمة تشمل معرف السطر والطلب والمنتج، واسم المنتج ورقمه وصورته والمقاس والكمية والسعر؛ لا تشمل بيانات الزبون. هذا إثبات أهلية تاريخية، وليس إثبات هوية المقاس الأصلي.

أداة محلية صريحة `--prepare-legacy-review` تقبل مسارين منفصلين وبصمة مصدر متوقعة. يجب أن يكون مصدر الإثبات السابق للهوية بلا عمود `ProductSizeId` وبلا Migration الهوية في سجله، وأن يكون سليماً ومطابق البصمة. تُقارن الأسطر بالأصل وتُجهز بيانات الإثبات فقط للأسطر المطابقة التي ما زالت بلا هوية؛ لا يُستعمل `CreatedAt` أو علم يرسله المتصفح لتحديد الأهلية.

تستورد Migration المتابعة الإثبات المجهز، ثم تحذف جدول التجهيز وتغلق إدخال الإثبات بtrigger دائم. تغير لقطة السطر لاحقاً يُبطل مطابقته. إعادة إدراج معرف سطر تاريخي مسجل بعد حذفه محظورة أيضاً. لا يوجد زر بالواجهة أو endpoint تطبيق لإضافة أهلية أو إلغاء هذه القيود.

إذا كانت بيئة قد طبقت Migration الهوية بالفعل، يمكن تجهيز الإثبات **قبل Migration المراجعة** من نسخة موثوقة تسبق الهوية، للأسطر التي ما زالت مطابقة فقط. النسخة الحالية بعد الهوية وحدها لا تصلح دليلاً تاريخياً. إذا طُبقت Migration المراجعة دون تجهيز إثبات، تبقى تلك الأسطر محظورة؛ إدخال إثبات لاحق يحتاج إجراءً مستقلاً مدروساً أو Migration متابعة، ولا يُحل بتصنيف جميع NULL كقديمة.

## D. موضع الميزة واستعمال المدير

تظهر داخل إدارة الطلبات عند حفظ انتقال إلى Cancelled أو الخروج منها لطلب يتضمن سطراً تاريخياً. يُعرض الطلب والحالة المصدر والحالة المطلوبة واتجاه الحركة والأسطر الأصلية. كل قائمة تبدأ بلا اختيار، حتى عند وجود مرشح واحد مطابق بالاسم أو مقصد سابق وحيد.

1. يختار المدير مقاساً حالياً صالحاً لكل سطر تاريخي، تابعاً إلى **ProductId الأصلي نفسه**. تعرض القائمة الاسم والكمية ومعرفاً مختصراً مميزاً، ويظهر المعرف الكامل ومعلومات المقصد المختار أسفلها.
2. يكتب سبب المراجعة، ويتحقق من أي حركة يدوية تمت خارج النظام كي لا يُكررها. لا يقدم البرنامج خيار «تجاهل المخزون».
3. يطلب المعاينة: تجمع الكميات لكل `ProductSizeId`، بما فيها الأسطر الحديثة المختلطة، وتعرض الإضافة/الخصم والمخزون الفعلي قبل/بعد.
4. يؤكد صراحة. لا ينفذ تغيير قائمة الحالة أو المقصد أي حفظ، ولا يكفي إغلاق المعاينة أو اختيار المقاس للموافقة.
5. بعد النجاح يظهر سجل التسوية الإدارية داخل تفاصيل الطلب: المدير، UTC، السبب، الحالات، المعرف الثابت، العملية السابقة، والحركات الفعلية.

الإغلاق أو الإلغاء لا يحفظ ربطاً أو حركة أو حالة أو تدقيق نجاح. فشل التعارض يبقي الاختيارات قدر الإمكان، ويلغي المعاينة القديمة ويطلب معاينة جديدة. عند احتمال ضياع الرد يحتفظ المسار بمعرف العملية وتذكرتها نفسها لإعادة محاولة آمنة؛ الخادم يعيد التحقق أو يسترجع النتيجة المحفوظة.

إذا احتوى تحديث جماعي طلبات تحتاج مراجعة، يُرفض كله وتظهر قائمة منظمة بالأسباب وروابط لفتح المراجعة الفردية. كل تسوية فردية عملية مستقلة. إعادة المحاولة الجماعية تقرأ الحالات الحالية، فتُعامل الطلبات التي وصلت إلى الحالة المطلوبة كـno-op.

## F. الذرية والتزامن ومنع التكرار ودورات الحالة

المعاينة لا تعدل الأعمال ولا تُبقي قفل DB أثناء انتظار المدير. تذكرتها محمية بـASP.NET Data Protection، مرتبطة بالمدير والطلب والعملية والحالات والإصدار والأسطر والمقاصد والمخزون، وصلاحيتها قبل تنفيذ جديد 15 دقيقة. لا يقبل التأكيد كميات أو مخزوناً قبل/بعد أو هوية مدير بوصفها حقائق من المتصفح.

عند التأكيد يُفحص المدير على الخادم قبل الدخول وبعد الحصول على قفل الكتابة. داخل معاملة SQLite تُقرأ البيانات مجدداً، وتُحسب الحركات من الأسطر المحفوظة، وتُقارن مع ما وافق عليه المدير. شرط الكتابة يشمل هوية المقصد وملكيته واسمه ومخزونه وإصداره؛ يجب أن يتغير صف واحد لكل مقصد.

تضم المعاملة جميع الحركات والحالة و`InventoryRevision` وحالة `SalesHistory` عند انطباقها والتدقيق وسجل العملية. فشل كتابة أي جزء يرجع الجميع. لا تُعدل الأموال أو `CreatedAt` أو رقم الطلب أو حجوزاته أو لقطة الشراء أو Snapshot المبيعات المالي. تحديث الحالة و`UpdatedAt` وحقول حالة المبيعات فقط يحدث بعد النجاح؛ Sandbox لا يكتب SalesHistory.

`Orders.InventoryRevision` مستقل عن `NumberRevision`، ويزيد في كل انتقال فعلي، العادي والجماعي والتسوية. trigger يمنع تغيير الحالة دون الزيادة الصحيحة، ويمنع تغيير الإصدار مع بقاء الحالة. العودة إلى Status السابقة لا تجعل المعاينة القديمة صالحة.

`ProductSizes.ReviewRevision` يزيد عند تغير الكمية أو الاسم أو المفتاح. تُكتشف أيضاً دورة مخزون أو اسم تغير ثم عاد إلى قيمته؛ لا يعتمد كشف التعارض على مساواة القيم النهائية فقط. كمية المقصد صفر مسموحة، لكن حدود int ومجموع كل مقصد تُفحص قبل الكتابة.

`OperationId` مفتاح دائم. نفس العملية بنفس التذكرة والسبب بعد تطبيعه والمدير تُرجع النتيجة المحفوظة دون حركة إضافية، بما في ذلك بعد إعادة تشغيل العملية أو انتهاء صلاحية التذكرة أو تنظيف الطلب. نفس المعرف بمحتوى آخر يُرفض. استرجاع النتيجة يفحص الصلاحيات ولا يعيد الحالة الحالية إلى حالة قديمة. العملية المختلفة لا تتجاوز إصداراً سبق تغييره.

كل إلغاء/إعادة تفعيل جديدة تحتاج اختياراً ومعاينة وموافقة حالية ومعرفاً جديداً وسجلاً مرتبطاً بالسابق. عند وجود مقصد تاريخي موثق لا يُسمح بعكس الحركة على مقاس آخر. إلغاء → إعادة تفعيل → إلغاء يولد ثلاث عمليات منفصلة على المقصد نفسه؛ لا تُعاد موافقة قديمة تلقائياً.

الجداول مستقلة عن العلاقات الحية للمنتجات والمقاسات والطلبات. العلاقات بين رأس التدقيق وتفاصيله `Restrict`، ولا Cascade إلى البيانات الحية. triggers تمنع تعديل أو حذف الإثبات والتدقيق، فيبقى بعد تنظيف الطلب أو حذف المقصد. القراءة والتأكيد واسترجاع النتيجة والتدقيق محمية بمصادقة الإدارة الحالية، ولا تُضاف بياناتها إلى «طلباتي» أو Store Chat.

## J. خطة النشر والتراجع لاحقاً — لم تُنفذ

1. وقت التنفيذ، أوقف كُتّاب البيانات وخذ نسخة احتياطية حديثة ومتسقة، ثم تحقق من البصمة وintegrity/FKs وآخر Migration وتشخيص المقاسات والحالات. نسخة 5 أكتوبر هنا دليل اختبار، وليست قاعدة تحل محل الإنتاج الذي يواصل استقبال الطلبات.
2. جرّب السلسلة على نسخة عمل جديدة خارج المستودع، مع مقارنة جميع الأعمال والحراس كما في الأداة أعلاه. إن كانت الإنتاج ما زالت قبل الهوية، فنسختها الحديثة السابقة للهوية تصلح مصدر الإثبات. إن كانت بعد الهوية، احتفظ أيضاً بمصدر موثوق سابق للهوية؛ لا تُصنف NULL الجديدة كقديمة.
3. جهز إثبات الأسطر المطابقة قبل Migration المراجعة، بينما التطبيق متوقف. الأداة موجودة في مشروع الـrunner وليست endpoint تطبيق. صيغة الأمر، على **نسخة العمل أولاً**:

   ```powershell
   dotnet run --project LaraFashion.IntegrationTests --no-build -- --prepare-legacy-review '<working-db>' '<trusted-pre-identity-evidence-db>' '<verified-sha256>'
   ```

4. بعد اعتماد نتيجة النسخة الحديثة وخطة التنفيذ، طبّق المخطط الكامل مع ملفات التطبيق المتوافقة في نافذة صيانة واحدة، ولا تشغّل التطبيق بين ترقية الهوية والمراجعة. لا تعمل نسخة التطبيق القديمة مع مخطط المراجعة: تغييرات الحالة القديمة لا تزيد الإصدار وسترفضها الحراس. لم يتغير مسار/إعداد الاتصال هنا.
5. تحقق بعد الترقية من إثبات الأهلية والحراس وسلامة القاعدة وتطابق الأعمال وعدم وجود تسويات Migration، ثم شغّل التطبيق المتوافق. أجرِ اختباراً اصطناعياً معزولاً، واترك قرارات الطلبات الحقيقية للمدير من واجهة المراجعة عند الحاجة. لا ترفع نسخة الاختبار مكان الإنتاج، ولا تستورد fixtures أو تذاكر الاختبار.

التراجع قبل أي تسوية ممكن بعد إيقاف الكُتّاب وفحص نسخة حديثة؛ `Down` يزيل مخطط المتابعة فقط مع إبقاء ترقية الهوية السابقة. استُخدم SQLite native `DROP COLUMN` للحفاظ على triggers السابقة، واختُبر على المحرك الفعلي `3.46.1`. إعادة نشر قديمة أو الرجوع إلى ما قبل الهوية يتطلب خطة منفصلة وفحصاً للبيانات الجديدة.

بعد وجود أي `OrderInventoryReviews`، **Down يتوقف قبل الحذف** لحماية التدقيق. المسار المناسب حينها إصلاح للأمام مع الاحتفاظ بالسجل، وليس إسقاط الجداول أو إعادة نسخة احتياطية قديمة تفقد الطلبات والحركات اللاحقة. أي استعادة من backup أو تصحيح تسوية خاطئة تحتاج قراراً مستقلاً وخطة حفظ الأعمال، وليست جزءاً من هذه المهمة.

إذا فشل فحص المقاسات أو الإثبات أو المقارنة الحديثة، يُوقف النشر وتُعالج الحالة المحددة. الحالات التي فقدت منتجها/مقصدها لا تُحل بإعادة إنشاء اسم مماثل أو ربط تخميني، ولا تُخفى تحت إعلان جاهزية شامل.
